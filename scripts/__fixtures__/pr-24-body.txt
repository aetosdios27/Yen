Stacked on #20 (it needs migration 0003); retarget to `main` after #20 merges.

## What this does

Moves the two in-memory API stores into Postgres so a second API instance shares them. Before, a duplicate request could run once per instance and a per-IP limit multiplied by the instance count.

- **`PostgresIdempotencyStore`** on `idempotency_keys`: atomic reserve with `INSERT ... ON CONFLICT DO UPDATE`, a 30 s lease that another request can take over once it expires, a fencing token so a stale worker cannot complete or release a taken-over key, and a retention sweep (24 h replay by default).
- **`PostgresRateLimitStore`**: a shared token bucket in `rate_limits`, read-modify-write under a per-key advisory lock, with a prune job.
- **Trusted-proxy client IP**: `createClientIpResolver({ trustedHops })`. With zero hops, `X-Forwarded-For` and `Forwarded` are ignored and the socket address is used. Also parses RFC 7239 `Forwarded`.
- One conformance suite runs against both the memory and Postgres stores, and a multi-process test starts two OS processes on one database.
- Migration `0004_shared_stores.sql` (renumbered from 0003 to sit after `fund_events`).

## How it was checked

`pnpm verify` is green (21 of 21 tasks) on a fresh Postgres 16. API: 172 tests. I ran 8 mutation checks. Removing the begin takeover rule, the fencing token on complete or release, the replay expiry, the refill, the max-entries cap, the sweep condition, or the zero-hop IP rule each fails a test.

## Fixed during review

Removing the rate limiter's advisory lock left every test passing, so nothing proved the lock does anything. I added a test where 60 parallel consumers share a 10-token bucket and exactly 10 must be admitted. Without the lock it fails on every run (3 of 3).

## What this does not claim

- **Clock skew.** Leases and buckets use the API process clock, not Postgres time. Instances whose clocks differ by more than the 30 s lease could take over a live key. Fine with NTP-synced hosts; moving to database time would remove the assumption.
- **Slow handlers.** A request still running past its 30 s lease can lose its lease. Completing it then fails rather than overwrite the new owner. Long operations need a longer lease or a heartbeat.
- **Cost.** Every limited request now opens a transaction and takes an advisory lock. Whether Postgres is fast enough is for the load harness (YEN-54) to show; Redis behind the same interface remains the plan if not.
- A request that completes after its lease expired but before anyone took the key over is still accepted. That is intentional.
