# Notification delivery adapters

The local API defaults to its in-memory OTP provider. Production startup requires `DELIVERY_PROVIDER=external`, both channel configurations, DLT SMS identifiers, and webhook secrets. The selected channel is honored as requested; delivery does not switch channels silently.

The shared `DeliveryProvider` contract is used by the OTP flow and by `DeliveryChannelBridge` in the notification worker. The adapters return provider acceptance separately from terminal delivery. Before entering the network call, the worker atomically reserves the fund's daily message count and configured per-message cost, and writes a durable `sending` state with that cost on the outbox row. If a worker dies during the call, recovery dead-letters the row without resending it. The provider might have accepted the message; the outcome stays ambiguous until an authenticated status event arrives. The cost is a configured estimate reserved before sending, so it is retained on ambiguous outcomes and may conservatively include a send that failed before being billed.

## Exotel SMS

The Exotel adapter uses a form-encoded single-message send, per-logical-template and per-locale DLT IDs, `StatusCallback`, and the response SID described by [Exotel's opened Send SMS reference](REFERENCES.md#exotel-sms-api). The approved OTP message body is configured separately for English and Hindi and substitutes only the code; notification bodies come from the existing localized renderer. Exotel's opened documentation describes callback fields but no callback signature scheme. `EXOTEL_SMS_STATUS_CALLBACK_URL` must therefore point to a relay that forwards callbacks to Yen and signs the raw body using `X-Hub-Signature-256` and the configured relay secret. The `/exotel` endpoint accepts only those signed relay callbacks. Direct Exotel callback authenticity is not verified by this implementation. Exotel's reference marks the DLT entity ID mandatory for India and the template ID optional; Yen requires both in production configuration as specified by YEN-76.

## Meta WhatsApp Cloud API

The WhatsApp adapter uses the message endpoint listed in Meta's [public Postman request](REFERENCES.md#meta-whatsapp-cloud-template-send). Meta's archived official Node SDK documents template name, language, and body parameters, but the Postman request body panel did not render and the SDK wraps its Graph API request. The exact raw template request payload therefore remains **unverified against the active Meta documentation**. The archived SDK confirms the GET `hub.challenge` handshake and POST `x-hub-signature-256` header using the app secret, but does not specify the HMAC-SHA256 raw-byte calculation; that detail follows the YEN-76 task contract and remains **unverified against accessible Meta documentation**. The API version, base URL, template names, languages, and parameter ordering are configuration. No live provider was contacted.

The API accepts Meta status webhook events only after raw-body HMAC verification. Replayed statuses use a stable event key. Status callbacks may arrive out of order, so the store compares the provider timestamp before updating the row, including callbacks received before the send response has stored its provider ID. Provider IDs, status, and estimated message cost are stored; phone numbers and message content are not written into delivery logs.

## Run the opt-in provider sandbox check

YEN-8 must supply provider sandbox/test accounts, approved templates and an allowlisted test handset before this check can demonstrate delivery. No provider account exists yet. Local HTTP adapter contract tests do not prove handset delivery.

1. Load sandbox-only credentials from your secret manager into the environment; do not paste them into shell history, command arguments, logs or the repository. Use the existing configuration names: `WHATSAPP_API_BASE_URL`, `WHATSAPP_API_VERSION`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_TEMPLATES_JSON`, `EXOTEL_SMS_ENDPOINT`, `EXOTEL_SMS_STATUS_CALLBACK_URL`, `EXOTEL_API_KEY`, `EXOTEL_API_TOKEN`, `EXOTEL_SENDER_ID`, `EXOTEL_DLT_ENTITY_ID` and `EXOTEL_SMS_TEMPLATES_JSON`. Both template maps use the production configuration schema, including the OTP code parameter and the approved English/Hindi SMS bodies. Point the callback URL at the sandbox's signed relay described above.
2. Set `YEN_SANDBOX_PHONE` to the provider-allowlisted handset in E.164 format. Check that both accounts, endpoints and the recipient belong to the sandbox. The adapters use provider-supplied endpoints; the runner cannot determine whether an account is a production account.
3. Build the dependencies with `pnpm turbo run build --filter='@yen/notifications^...'`.
4. From a local shell with `CI` unset, run `YEN_DELIVERY_SANDBOX=1 pnpm --filter @yen/notifications test:sandbox`. This sends one randomly generated six-digit code through each adapter, with no retry. These are delivery probes, not active login challenges. No credentials, phone numbers, codes or provider response bodies are printed by the test.
5. Confirm one code arrives in WhatsApp and one in SMS on the test handset. The automated assertions prove provider acceptance only. Confirm terminal delivery through the authenticated status callbacks as well. Record the date, channel and acceptance/delivery outcome without recording the code or phone number. A green acceptance test alone does not satisfy the real-delivery acceptance criterion.

Without explicit opt-in or any required credential/configuration value, both tests skip cleanly. Invalid complete configuration fails with a generic error. Any defined `CI` variable disables sends, even with opt-in and credentials. Normal `pnpm test` and `pnpm verify` exclude `sandbox/**/*.sandbox.ts`; no CI workflow invokes `test:sandbox`.

Interrupted sends remain visible as dead letters and are not automatically replayed. Without provider-supported idempotency or reconciliation, the worker cannot guarantee that an interrupted network send reaches the handset exactly once. Operators must reconcile ambiguous rows before considering a manual resend; see the `sending` recovery behavior above.
