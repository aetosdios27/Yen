# Security review — October 2026

## Method and scope

Reviewed `origin/main` at `0182c1c6e00e65752cbe04072ac5f419b0063d4f` in an isolated worktree. Read `README.md`, `SECURITY.md`, `docs/THREAT-MODEL.md`, `docs/TRUST-CLAIMS.md`, and `docs/REFERENCES.md`, then traced the relevant handlers, stores, ledger operations, migrations, tests, web configuration, workflows, and contract code. Findings below are based on source paths and test behavior cited at the point of use. I did not run exploit scripts.

The review covered API authorization/redaction, expense approve/reject/pay/reconcile, PIN HMAC and lockout, holds/settlement/refunds/expiry, idempotency, OTP/session/trusted-device/invite flows, event schemas/hashes/database append controls, pseudonyms, anchoring/KMS/`RootRegistry`, evidence upload/scanning/storage, web XSS/CSRF/CSP/headers, and CI/supply-chain controls.

**Reachability limit:** `startServer` wires Postgres auth, PIN, expense, pledge, and reconciliation stores, but does not wire a persistent `fundStore` or an allowing production policy (`apps/api/src/server-bootstrap.ts:144`, `apps/api/src/dependencies.ts:252`). The default policy is deny-all (`apps/api/src/dependencies.ts:282`). Therefore findings about protected expense actions describe what their handlers do when a deployment grants the corresponding `can()` action; those actions are denied by the committed default bootstrap. The unauthenticated webhook is reachable independently of those protected routes.

## Findings

### High

#### SEC-1 — Partner webhook accepts unauthenticated bank assertions

**Evidence:** the global auth gate only covers `/v1/funds/*` and `/v1/auth/*` (`apps/api/src/app.ts:297`); the webhook handler parses caller JSON and immediately calls `reconciliationStore.ingest` (`apps/api/src/app.ts:1727`). Its schema validates fields but has no signature or sender-authentication input (`apps/api/src/reconciliation/partner-schema.ts:9`). Postgres ingestion inserts the supplied transaction and exact-matches credits to pledges (`apps/api/src/reconciliation/postgres-store.ts:83`, `apps/api/src/reconciliation/postgres-store.ts:102`); an exact UTR and amount yields a match (`apps/api/src/reconciliation/matching-engine.ts:54`). The existing webhook test sends the request without authentication headers (`apps/api/src/reconciliation/reconciliation.test.ts:179`).

**Scenario:** any internet client can persist fabricated, immutable bank transaction rows using unique references. If a supplied credit matches a pending pledge's UTR and amount, ingestion calls `reconcilePledge`, which changes the pledge to verified and posts the value into the ledger (`packages/ledger/src/operations.ts:531`). The transaction table has no `fund_id` foreign key (`packages/db/migrations/0019_bank_transactions.sql:5`), so even invented fund IDs can create unmatched records.

**Fix:** authenticate the partner using a MAC/signature over the exact raw request bytes before parsing or ingestion; enforce timestamp/replay bounds and retain idempotent reference handling. Add tests for missing, invalid, tampered, stale, and valid signatures.

**Tracking:** [GitHub issue #102](https://github.com/aetosdios27/Yen/issues/102) (`security`, `priority: urgent`).

#### SEC-2 — Concurrent wrong PIN attempts lose lockout increments

**Evidence:** PIN verification reads a record, computes absolute counters from that snapshot, and later updates them (`apps/api/src/pin/service.ts:173`, `apps/api/src/pin/service.ts:243`). The Postgres update reads the current row and writes the caller-supplied absolute values without a row lock or compare-and-swap (`packages/db/src/approval-pin.ts:63`). Existing integration tests verify lockout sequentially (`apps/api/src/pin/pin.integration.test.ts:275`).

**Scenario:** several concurrent wrong-PIN requests can all read `failedAttempts = 0`, each calculate `1`, and overwrite the row with `1`. An attacker with a valid trusted session can exceed the intended five-attempt/30-minute and ten-attempt/24-hour limits by sending guesses concurrently. This defeats a key control on the low-entropy approval PIN.

**Fix:** perform verification-failure accounting as a serialized database operation, deriving both counters and lock state while holding the PIN row lock or using an atomic conditional update. Add a Postgres concurrency regression test.

**Tracking:** [GitHub issue #103](https://github.com/aetosdios27/Yen/issues/103) (`security`, `priority: high`).

### Medium

#### SEC-3 — Expense reconciliation accepts an unverified transaction ID

**Evidence:** the pay handler accepts `input.bankTransactionId` and stores the resulting paid expense after checking only that the expense is approved (`apps/api/src/app.ts:1167`). `payExpenseInTx` commits the hold and records that caller-supplied ID (`packages/ledger/src/expense/service.ts:297`). Reconciliation only compares the new ID with the stored ID, then appends `bank.debit_seen`; it does not query `bank_transactions` (`apps/api/src/app.ts:1213`, `packages/ledger/src/expense/state-machine.ts:337`, `packages/ledger/src/expense/service.ts:351`). The existing test checks only that a different ID is rejected (`packages/ledger/src/expense/service.test.ts:97`).

**Scenario:** a principal allowed to pay and reconcile an approved expense supplies any syntactically valid transaction ID at `/pay`, then reuses it at `/reconcile`. The expense becomes reconciled and a bank-debit event is appended even if no bank transaction exists or its amount differs. The committed server's default deny-all policy currently blocks these protected actions; the invariant must hold when an allowing policy is wired.

**Fix:** resolve the supplied transaction against an ingested immutable bank row for the same fund, require debit type and exact amount, and bind that row to only one expense inside the settlement transaction.

#### SEC-4 — EXIF-stripped image bytes are discarded

**Evidence:** upload stores original bytes, then computes `_sanitizedPreviewBytes` without using it (`apps/api/src/app.ts:1611`). The authenticated proof response reads and returns the original stored bytes (`apps/api/src/app.ts:853`). The integrity helper verifies those original bytes against their original hash (`apps/api/src/integrity-job.ts:45`).

**Scenario:** an uploaded photo with GPS or device metadata is available as raw base64 to authorized evidence readers, despite the upload code's stated privacy intent to strip EXIF. Location or device details can disclose information unrelated to the receipt.

**Fix:** keep the original as a restricted integrity artifact and persist/serve a separately hashed sanitized preview, or remove the unused sanitization claim and clearly restrict original access.

#### SEC-5 — Production anchoring can silently fall back to a software key

**Evidence:** when `ANCHOR_KMS_KEY_ID` is absent, the worker CLI unconditionally constructs `LocalDevRootSigner` from `ANCHOR_PRIVATE_KEY` (`packages/queue/src/cli.ts:43`). The worker environment parser does not gate that branch on production mode. The README describes the signer as a local fallback (`packages/queue/README.md:18`).

**Scenario:** a production anchoring worker configured with RPC/address and a private-key environment variable but no KMS key will sign using the hot process key instead of refusing to start. Host or environment compromise then exposes publication authority.

**Fix:** require KMS in production and allow the software signer only under an explicit development/test mode; fail startup otherwise.

### Low

#### SEC-6 — The repository does not set browser security response headers

**Evidence:** Next configuration returns only a build ID (`apps/web/next.config.ts:11`), and `apps/web/vercel.json:1` contains no response-header rules. A source scan found no CSP, `X-Frame-Options`, `X-Content-Type-Options`, or `Referrer-Policy` configuration. I found no `dangerouslySetInnerHTML`, direct `innerHTML`, or `eval` usage in the web source.

**Scenario:** if a future injection bug reaches a page, there is no repository-defined CSP to constrain script execution; clickjacking and MIME-sniffing protections also depend on deployment configuration outside this repository.

**Fix:** configure a tested CSP and appropriate framing, MIME-sniffing, and referrer headers in Next or the deployment edge.

## Checks that passed by source inspection

- **Authorization and redaction:** protected expense handlers call `authorizedExpense`, which requires `deps.policy.can()` (`apps/api/src/app.ts:900`); resource responses pass through the policy redactor (`apps/api/src/app.ts:916`). Approvals require separation of duties and the route checks the requester before verifying action-bound PIN proof (`apps/api/src/app.ts:1034`, `apps/api/src/app.ts:1036`). The webhook exception is SEC-1.
- **Money representation and transitions:** expense wire amounts are canonical paise strings; ledger amount inputs use safe integers and `BigInt` for postings (`packages/ledger/src/operations.ts:618`, `packages/ledger/src/operations.ts:624`). Expense state transitions reject out-of-order states, and Postgres expense mutations lock the expense row (`apps/api/src/expense-store.ts:80`).
- **Holds, refunds, and idempotency:** expense holds use a per-fund advisory lock and a domain idempotency key (`packages/ledger/src/expense/service.ts:291`, `apps/api/src/expense-store.ts:96`). Refunds require a verified donation and reject a second refund (`packages/ledger/src/operations.ts:1116`, `packages/ledger/src/operations.ts:1128`). HTTP idempotency binds the key to method, path, content type, and body, and stores completed responses (`apps/api/src/middleware.ts:281`, `apps/api/src/middleware.ts:302`, `apps/api/src/middleware.ts:345`). Pledges also have a unique UTR constraint (`packages/db/migrations/0011_donation_pledges.sql:15`).
- **OTP, sessions, and invites:** OTPs are random six-digit codes with keyed HMAC storage (`apps/api/src/auth/crypto.ts:6`, `apps/api/src/auth/crypto.ts:20`); Postgres enforces cross-channel phone attempt limits atomically (`apps/api/src/auth/stores.ts:532`), and a challenge is consumed once (`apps/api/src/auth/stores.ts:617`). Sessions are 256-bit random bearer tokens stored by SHA-256 hash (`apps/api/src/auth/crypto.ts:36`, `apps/api/src/auth/crypto.ts:43`); cookies are `HttpOnly`, `Secure`, and `SameSite=Lax` (`apps/api/src/app.ts:503`). OTP tests cover same-error behavior for unknown phone and invalid code (`apps/api/src/auth.test.ts:455`) and cross-channel limits (`apps/api/src/auth.test.ts:415`). Invites use 32-byte random codes stored as hashes, expire after five minutes, are phone-bound, require owner confirmation, and create a member-only lower-assurance identity (`apps/api/src/auth/invite-routes.ts:42`, `apps/api/src/auth/stores.ts:664`, `apps/api/src/auth/stores.ts:695`). The verify and rotate responses also include the bearer token in JSON (`apps/api/src/app.ts:511`, `apps/api/src/app.ts:547`); browser clients must treat that response body as sensitive even though the cookie is HttpOnly.
- **Event log and pseudonyms:** event types use strict schemas; actors and member IDs are pseudonyms, and payload schemas contain no user UUID, phone, display name, or contact field (`packages/eventlog/src/model.ts:43`). Canonical hashing sorts object keys and rejects unsupported JSON values (`packages/eventlog/src/canonical.ts:14`); event hashes are domain-separated SHA-256 over the canonical envelope (`packages/eventlog/src/chain.ts:26`). Appends serialize per fund and chain to the current event head (`packages/db/src/events.ts:263`). Database triggers and grants block event update/delete/truncate (`packages/db/migrations/0003_fund_events.sql:582`); tests cover concurrent appends and immutability (`packages/db/src/events.test.ts:169`, `packages/db/src/events.test.ts:720`). Per-fund random pseudonyms are tested for unlinkability across funds (`packages/db/src/pseudonyms.test.ts:50`).
- **Anchoring and contract:** KMS signing validates secp256k1 key material and recovered signer address (`packages/queue/src/anchoring.ts:108`); reconciliation recomputes the root and compares it with the persisted and on-chain roots (`packages/queue/src/anchoring.ts:301`, `packages/queue/src/anchoring.ts:328`). `RootRegistry` accepts only the publisher, enforces nonzero sequential roots, and has no upgrade or funds path (`contracts/src/RootRegistry.sol:29`, `contracts/src/RootRegistry.sol:44`). A confirmed depth is not finality and a chain reorg is not automatically repaired (`packages/queue/README.md:44`).
- **Uploads:** MIME allowlist excludes HTML/SVG and checks binary signatures (`apps/api/src/mime-signature.ts:7`); route and streaming limits cap evidence at 10 MiB (`apps/api/src/app.ts:277`, `apps/api/src/app.ts:1539`). The ClamAV adapter has an environment-configured host, maximum size, and timeout; errors become quarantined (`apps/api/src/virus-scanner.ts:56`), and the upload route rejects thrown, infected, or quarantined results (`apps/api/src/app.ts:1583`). Storage keys are opaque random identifiers and filenames are reduced to a basename (`apps/api/src/storage.ts:33`, `apps/api/src/storage.ts:46`). No caller-controlled URL or path is fetched, so I found no SSRF or path traversal path in this flow.
- **Web and CSRF:** React escapes rendered values; no unsafe HTML sink was found in the source scan. Session cookies use `SameSite=Lax`, and CORS is restricted to configured origins, methods, and headers without credentials (`apps/api/src/app.ts:201`). I found no browser cross-site write path that bypasses JSON parsing and CORS, so no CSRF finding is reported.
- **CI and supply chain:** workflow actions are pinned to full commit SHAs; CI grants read-only repository permissions by default, disables checkout credential persistence in pull-request and release jobs, runs Gitleaks and high-severity dependency review, and CodeQL uses the extended query set (`.github/workflows/ci.yml:9`, `.github/workflows/ci.yml:107`, `.github/workflows/ci.yml:124`, `.github/workflows/codeql.yml:26`). Release artifacts include a CycloneDX SBOM, provenance attestation, and keyless Cosign bundle (`.github/workflows/release.yml:51`, `.github/workflows/release.yml:94`, `.github/workflows/release.yml:104`). Dependency versions resolve through `pnpm-lock.yaml` integrity hashes and CI installs with `--frozen-lockfile` (`.github/workflows/ci.yml:46`).
